## [0.0.25] - 2026-11-08
### Added
- `OffloadHandle.release_gpu()` and `restore_gpu()`: move the weights of the blocks that stay on the GPU to ordinary CPU memory and back, keeping the hooks, so the VRAM is free between two calls of the model. Each returns the bytes moved and does nothing (returns 0) when called twice in a row. A block in the compute dtype moves with `Module.to`; a wrapped block (fp8 with scales, or a dtype that differs) moves its stored weights and scales in place with `.data` (`_move_entry`), so the module and the entry still hold the same tensors. Blocks register a `(release, restore)` pair in `OffloadHandle._resident` (merged by `extend()`) when they are installed on a CUDA device; blocks on the CPU, in RAM or on disk register nothing
- `_Prefetcher.quiesce()`, called first by `release_gpu()`: drops the staged blocks, waits for the worker, the staging stream and the blocks in flight, and sets the start of the pass in progress to `None`, so the pause between two calls is not logged in `pass_waits` as a slow pass (the look-ahead tuner reads it). `release_gpu()` ends with `torch.cuda.empty_cache()`
- Blocks whose weights are loaded while the model runs (`overlap=True`) join the registry of the outer handle when their hooks go in, at their first call. `OffloadHandle._deferred` counts those that have not; `release_gpu()` raises a `RuntimeError` while it is not 0
- README: a paragraph in "Running a stage", a bullet in "What we measured"; the roadmap item for `release_gpu()` / `restore_gpu()` is removed

### Notes
- A wrapped block still runs while it is released: its weights are on the CPU, so it stages from RAM like a RAM-tier block, with the same output. A block in the compute dtype does not (device mismatch); `restore_gpu()` has to come first. The weights outside the blocks stay on the GPU. There is no guard against calling either method while the model runs
- Cost on the RTX 3060 (torch 2.8.0), stand-in blocks of two 4096 x 4096 linear layers built on the GPU (67 MB in bf16, 34 MB in fp8 with a scale), 1 warm-up and 5 measured cycles, medians: bf16 1 GB 0.22 s out and 0.27 s back, 2 GB 0.45 s and 0.58 s, 4 GB 1.04 s and 1.27 s; fp8 1 GB 0.23 s and 0.28 s, 2 GB 0.50 s and 0.61 s, 4 GB 1.04 s and 1.32 s. That is 3.9 to 4.6 GB/s out and 3.0 to 3.7 GB/s back, the same for both kinds. The driver reported 1.0 to 4.1 GB more free VRAM after the release. The first forward pass after the restore took 400 ms against 384 ms for fp8 at 4 GB and 29 ms against 24 ms for bf16 (within the noise of the run)
- RAM while released equals the stored size of the resident blocks, in pageable memory. The process's private memory grew by 1.2 GB for 2 GB and 3.5 GB for 4 GB, a rough reading that is noise below 1 GB. One 1 GB tensor moved to the GPU at 5.1 GB/s from pageable memory and 12.9 GB/s from pinned memory, so the restore could be about 2.5 times faster with pinned copies, which would need pinned RAM as large as the weights; they were not tried. With 2.6 GB of RAM free the copy to the CPU fell to 1.2 GB/s (3.3 to 5.8 GB/s with more free)
- Not measured: sizes above 4 GB (the free RAM was between 2.6 and 9.7 GB during the run), another machine, and the cost against reloading the resident blocks from the file. It has not been run on the diffusion model pipeline, and the deferred-block path is tested with a stand-in block only
- Checked on the GPU: the output after `restore_gpu()` is bit-identical to the output before `release_gpu()` for blocks in fp32, wrapped blocks in bf16 and fp8 blocks with scales; the allocator gave back at least the bytes reported; a wrapped block gave the same output while released; 119 fp8 blocks made 6 cycles with the bytes out equal to the bytes back. With the reset of the pass start taken out of `quiesce()`, the two tests for it fail
- 394 tests = 9 new

## [0.0.24] - 2026-11-08
### Added
- `TRASH_PANDA_ADAPTIVE_LOOKAHEAD` (`adaptive_lookahead` in `config.py`, default off) and `TRASH_PANDA_LOOKAHEAD_MAX` (`lookahead_max`, default 4): the look-ahead follows the passes. A `DepthTuner` (new module `offload/depth.py`) hill-climbs on the measured pass time: it leaves out the first 2 passes (cold reads) and the pass after each change, compares the median of 2 passes, stops at once if the main thread waited less than 10% of the pass (nothing to gain), and otherwise raises the depth by one and keeps it only if the passes got at least 3% faster, up to `lookahead_max`; a depth that did not pay off is given back and it stops for good. Where the main thread waited less than 10%, it tries a look-ahead of 1 instead and keeps it if the passes are not more than 2% slower (otherwise the depth goes back). A deeper look-ahead stages more blocks on the GPU than the plan counted on, so it is only taken when the driver reports free VRAM (outside PyTorch's cache, which the activations may need) for the extra blocks and a margin of 5% of the GPU (at least 256 MB); if not, the depth stays and the tuner stops. The pinned buffers grow to match (`_PinnedPool.grow()`). With the setting off there is no tuner and nothing changes
- The prefetcher measures, with no profile, how long the main thread waited for staged blocks in each pass: `waited` (seconds so far) and `pass_waits` (the last 64 finished passes as `(seconds the pass took, seconds waited)`; a pass is logged when the next one starts, so it also includes any time the caller spends between two calls). It costs two `perf_counter` calls per staged block; the profile report is unchanged. The start of a pass no longer depends on the profile
- The staging that a stage does not use goes to the next model. When the tuner lowers the look-ahead, the prefetcher writes the room of the blocks it no longer stages to the plan it serves (`Plan.spare_staging_bytes`, the number of blocks lowered times the largest block staged, 0 when the depth is back at the planned one). `preload(running=plan)` gives that figure to the early loader as credit (`_EarlyLoader(..., credit=)`, a function that is read each time): the loader may load that many bytes of the next model before the running model frees anything, on top of the memory its final pass frees. The GPU still has to have room for the block (the same check as before). The running stage's plan is the one passed as `running=`; `_expected_after()` does not count the spare, because staging that is not allocated is in the free memory already
- README: the two settings in the table, the measurements below in "What we measured", a paragraph in "Loading the next model while one runs"; the roadmap item for the depth of the staging is removed

### Notes
- Stand-in models on the RTX 3060 (torch 2.8.0): 12 blocks of 2048 x H, stored as float32 and expanded to bf16 when they run, 1.5 GB per model, the file in the file cache (so no read was cold), compute of a block set with a GPU sleep. Median pass time over 6 passes, single runs, look-ahead 1, 2, 4 and 8 with the default 2 pinned buffers and, for 4 and 8, with as many as the look-ahead. With no compute (the copies set the pace) the pass took about 250 ms at every depth. With 20 ms per block (12 x 20 = 240 ms of compute) the pass took 258, 252, 251, 249 and 247 ms in the uniform case (2/2, 4/2, 4/4, 8/2, 8/8), 270, 256, 249, 260 and 250 ms with varied block sizes and 275, 267, 262, 265 and 264 ms with every fourth block on the disk tier; look-ahead 1 was 10% to 19% slower. With 100 ms per block (the compute sets the pace) every depth gave 1151 to 1165 ms and the main thread's wait fell from 14 to 31 ms to 0.1 ms. Runs of the same setting differed by up to 5%, so differences under about 3% are noise
- The wait alone does not predict a gain: it was about 80% of the pass with no compute (no gain) and about 55% with 20 ms (a gain), which is why the tuner tries a depth and compares the passes. The wait that is counted is only the wait for staged blocks: at look-ahead 1 it was lower (112 ms against 198 ms) with the same pass time, and where the rest of the waiting went was not traced
- The adaptive setting on the same models, 30 passes, start 2, at most 4, median of the last 10 passes against fixed 2/2 (mean of two runs) and fixed 4/4: compute-bound cases unchanged (about 1156 ms) and the depth never moved; with 20 ms per block: uniform 245.8 against 247.2 and 245.8 (depth stayed 2), varied 258.4 against 261.1 and 249.6 (depth stayed 2, so the gain was missed), disk 258.9 against 273.5 and 258.2 (depth 3, the gain was found). With no compute it tried depth 3 for a few passes and went back. It misses a gain that only shows at the deepest setting, because it steps one block at a time
- The spare staging, on the same models: stage A of 12 blocks of 0.07 to 0.54 GB with 100 ms of compute each (compute sets the pace), 16 passes, then `preload(running=, after=)` of a second model of the same shape before A's final pass. With the setting on, A's look-ahead went to 1 and its plan reported 268 MB of spare staging (one block of its largest, 268 MB); two blocks of the next model (134 and 33 MB) loaded before the final pass began, and its output equalled a reference computed without trash-panda. With the setting off, A kept look-ahead 2, the spare was 0 and nothing loaded before the final pass. A's pass took 1153 and 1163 ms before and 1162 and 1169 ms after the change (+0.8% and +0.5%), against 1151 and 1150 ms and 1153 and 1154 ms with the setting off. Two runs of each; the stage had no GPU-resident blocks, so its final pass freed no VRAM and nothing more of the next model loaded
- Checked on the GPU: with the setting off the look-ahead and the pinned pool never change over 20 passes; with it on, the output of 20 passes was bit-identical to the run with it off while the depth went 2, 3, 4, 3, and it stayed within 2 to 4 with a pinned pool at least as large; with the GPU full (0 MB free) the depth never left 2 and nothing failed; the tuner stopped within 30 passes
- What the staging that is not used is worth depends on the model: one block, 268 MB here, 0.43 GB for the diffusion model of the test pipeline, whose blocks are compute-bound, so the look-ahead of 1 is the case there. The tuning of the rules (the 3% and 2% limits, a deeper first step) is left for faster hardware, where the compute of a block is closer to its copy time and the effect should be larger. It has not been run on the diffusion model pipeline, whose blocks are compute-bound (about 0.2 s of compute against about 0.03 s of copy per block), so no gain is expected there
- 385 tests = 28 new

## [0.0.23] - 2026-11-06
### Added
- `preload(..., running=None)`: the plan of the running stage (the `p` of `with stage(...) as (a, p, handle)`). When it is given, `max_vram` and `max_ram` can be left out: the VRAM the model can count on after the release is the VRAM free now plus the running stage's GPU blocks and weights outside the blocks, and the RAM is the RAM free now plus the running stage's RAM tier. The running stage's buffers and activations are not counted, so the VRAM figure is low, never high; a mapped RAM tier gives back only the pages that were touched, so the RAM figure can be high. A figure that is given wins. With `TRASH_PANDA_PROFILE=1` it prints what it planned for
- Only part of the RAM tier is read early: `preload()` takes the RAM-tier blocks in the order they run (the `order` argument, the order file, else the plan's order), from the first one, until the next one does not fit in the RAM free now less `min_free_ram` and the pinned buffers, and reads those into memory of its own. The others stay mapped from the file and are read when they first run. `stream_load(..., ram_in_memory_prefixes=None)` reads only the RAM-tier blocks with those prefixes into memory (it replaces `ram_in_memory` when given); `ram_overhead(plan, hardware, min_free_ram)` in `planner.py` is the RAM that `plan()` keeps back (`min_free_ram` and the pinned buffers)
- The plan is fitted to the VRAM that is really free when a pending model is entered. A block planned for the GPU that is not there yet and does not fit goes to the RAM tier (mapped, `DeferredLoad.demote(prefix)`), with a `RuntimeWarning` that is also added to `plan.warnings`; blocks already on the GPU stay. Room that is left takes RAM-tier blocks that were read into memory, in the order they run, up to the first that does not fit; blocks that stayed mapped are not moved. Free VRAM is the driver's figure plus what PyTorch holds cached and unused, less the plan's headroom and the room for streaming blocks (the buffer, and the staged blocks when a block is outside the GPU). Nothing is changed when the free VRAM is not known. The decision is `refit_gpu_blocks()` in `planner.py`, which does not change the plan; `vram_kept_back(plan)` is the VRAM a plan keeps free
- `Plan.headroom_bytes`: the VRAM that `plan()` kept free for activations (the measured activation size plus its margin, or `headroom_vram`), which the replan needs because the VRAM budget is clamped to 0 when the model does not fit

### Changed
- `preload()` no longer cuts `max_ram` down to the RAM free now and no longer warns: the model is planned for the `max_ram` given (or the prediction), and only the part that fits in the free RAM is read early. `max_vram` and `max_ram` are optional keywords; a call with neither `max_vram` nor `running` raises `ValueError` (it was `TypeError` for a missing `max_vram`)
- The early loader keeps free the larger of its old margin (5% of the GPU, at least 256 MB) and `vram_kept_back(plan)`. Before, with less VRAM than the plan counted on, it could fill the GPU and leave the model no room for activations

### Notes
- Checked on the RTX 3060 (torch 2.8.0) with stand-in models of 8 blocks of about 134 MB, output equal to a reference computed without trash-panda in every case, and each block's tier equal to where its weights were: a plan whose VRAM budget was clamped to 0, entered with 0.75 GB free against a 1.5 GB headroom, put all 8 blocks in RAM; 8 blocks planned for the GPU with room for about 3 left 3 on the GPU and 5 in RAM; 2 blocks planned with plenty of room ended with all 8 on the GPU; with free RAM for 3 of 6 RAM blocks, 3 were read early and moved up and 3 stayed mapped; an open stage with `running=` and `after=`, where a tensor that the prediction did not know about left 0.83 GB free at entry against 11.67 GB predicted, loaded 3 blocks early, kept 3 on the GPU and put 5 in RAM. The first version of the last check showed that the early loader ignored the plan's headroom; that is the change above
- Timing of the partial read, with the files in the file cache so that no read was cold: the next model took 0.82 s after the running one with all RAM blocks read early and 0.64 s with part of them. That is not a result; the comparison that matters is the total time of a pipeline with a cold file
- With a model larger than the free RAM, blocks that stay mapped are read at the drive's pace when they first run (0.36 to 0.42 GB/s on the test machine's SATA drive), as in a model that was not preloaded. Reading them into memory after the release is not done; on a SATA drive it measured slower (see 0.0.19)
- It has not been run on the diffusion model pipeline
- 357 tests = 25 new

## [0.0.22] - 2026-11-04
### Added
- `record_order(build, path, *, args=(), kwargs=None, skip_prefixes=(), order_file_destination=None, groups=None)` finds the order in which a model runs its blocks before its first real run and saves it to the order file that `stage()` and `install_offload()` read. It builds the model on the meta device and calls it once with the inputs the caller gives (tensors in them are moved to the meta device), so no weights are read and nothing runs on the GPU. It replaces a file that is already there and never opens the checkpoint, only uses its name. When the call fails on the meta device (an operation without a meta version, or code that reads a tensor's values), or no block runs, it warns with a `RuntimeWarning`, returns `None` and saves nothing; it raises `ValueError` if `build()` returns a model with weights in memory. 17 tests
- `preload(..., after=None)`: with the queue that `handle.subscribe()` of the running stage returns, the next model's GPU blocks are loaded early, in the order they will run, as the running model's final pass frees the same number of bytes of GPU memory and the GPU has room for the block plus a margin (5% of its memory, at least 256 MB). Each block is copied through two small pinned buffers (64 MB each, apart from the running model's) on a copy stream of its own; the destination is allocated on the compute stream so it reuses the freed memory, and the copy waits for the event of the last freed block. The blocks not loaded early load when the pending model is entered; a failure in the early loading only gives a `RuntimeWarning`. The queue is read by the loader. New module `offload/early.py`. 19 tests
- README: `record_order()` in "Running a stage" and early loading in "Loading the next model while one runs"; the idea of reading the order from the source of `forward()` with `ast` is listed as out of scope, and the roadmap item for a better first order is removed; the roadmap item for loading into freed VRAM now lists what is left

### Changed
- `DeferredLoad.load(prefix)` skips a block that is loaded already and holds a lock, so two threads can share the work; it takes an optional `copy` function that replaces the plain `.to(device)` of the GPU tier

### Notes
- Tried on the diffusion model pipeline (RTX 3060 with 12 GB, 16 GB of RAM): the diffusion model (32 blocks, the four text blocks first and then the 28 main ones) and the VAE (6 blocks, called through `forward()` with an image and `skip_prefixes=("encoder.",)`, because its entry point `decode()` is not `forward()`) were recorded on the meta device. The text encoder (36 blocks) needed three changes to the call: no attention mask, `use_cache=False`, and a stand-in for the rotary embedding, because `torch.autocast` does not support the meta device. A run with the files they left used them with no order warning, in 93.7 s (the usual range is 94.9 to 98.3 s). All three models had order files already, so no speed difference is claimed; the call matters for a model that has never run
- A model whose entry point is not `forward()` cannot be recorded directly yet
- Early loading, measured with stand-in models (blocks of two 4096 x 4096 layers) on the RTX 3060, torch 2.8.0, single runs: a loader thread without a stream set reuses the memory the running model freed (2.8 to 2.9 GB reserved for 2.6 GB of blocks), but its copy from the memory-mapped file holds up the compute (the longest kernel launch took 36 to 46 ms against 0 to 1 ms alone, 11 to 15% fewer multiplications); copying through pinned memory did not, also with the destination allocated on the compute stream. Twelve blocks of 128 MB with the file in the file cache: all twelve loaded while the running model freed its own, entering the pending model took 0.31 to 0.35 s against 0.97 s, the next model took 2.2 to 2.4 s after the running one ended against 2.9 s, the running model's forward call did not change, and the reserved memory peak was the same. With only 2.6 GB of VRAM free, the two models of 1.6 GB did not fit together; 7 to 8 of 24 blocks loaded early (the file was not in the file cache, so the drive set the pace), the output checksum was the same as without early loading, and the next model took 1.50 to 1.53 s after the running one against 1.67 to 1.69 s
- A first version waited on an event recorded after each allocation, which stands behind everything the running model has queued, and each block took 0.6 to 0.8 s; waiting for the event of the last freed block fixed it. In the tight run, one run took 8.8 s for the running model with the GPU's free memory at 0.00 GB; a run without early loading took 3.0 s at the same point, so the cause is the full GPU and not only the loader, and the check for room was added
- Early loading with fp8 weights and per-tensor scales (the layout of the diffusion model of the test pipeline), stand-in models of 24 blocks of 33.5 MB stored, no memory pressure: all 24 blocks loaded early, entering the pending model took 0.15 to 0.17 s against 0.49 s, the next model took 0.79 to 0.84 s after the running one ended against 1.12 to 1.16 s, and its output was identical with and without early loading and equal to a reference computed from the checkpoint
- A block larger than the memory freed waits for room, and loads when the pending model is entered. Blocks larger than the freed ones need new memory, because the freed segments are not merged (probes: 4.9 to 5.3 GB reserved for 2.6 GB of blocks); `torch.cuda.empty_cache()` after the freed blocks' events gave full reuse for every shape (2.7 GB), at about 12 to 30 ms per call on the thread that calls it, but it is not used. On the test pipeline the step into the VAE is the smaller case and the step into the diffusion model the larger one
- It has not been run on the diffusion model pipeline. The tests and checks ran on the Python on the PATH (3.9, torch 2.8.0+cu126), not on the 2.5.1 that the pipeline uses
- 332 tests = 36 new

## [0.0.21] - 2026-11-04
### Added
- `preload(build, path, *, max_vram, max_ram, ...)` starts loading the next model of a pipeline while the current one is still running, and returns a `PendingStage` that is used like `stage()`: `with pending as (model, plan, handle):`. The model is planned when `preload()` is called, with the memory the caller says it will have (`max_vram` is required, because the GPU is in use by the running model; `max_ram` is cut down to the RAM that is free now with a `RuntimeWarning`, and `None` means the RAM that is free now). A background thread then runs `stream_load` with the GPU blocks deferred, so only the RAM tier is read, into memory of its own whatever `TRASH_PANDA_RAM_IN_MEMORY` says. The `with` block waits for the thread, loads the GPU blocks with the memory-mapped reads that `stream_load` uses (or starts the loader thread with `overlap=True`) and installs the hooks, so the GPU memory of the running model has to be free by then. An error in the reads is raised there, and the half-loaded model is freed. `cancel()` waits for the reads and frees what they loaded. A pending model can be entered once. The peak GPU memory is remembered under `key` as for `stage()`. With `TRASH_PANDA_PROFILE=1` it prints how long the background read took and how long the model waited for it. The weights outside the blocks are put on the GPU as soon as they are read
- `stream_load(..., ram_in_memory=None)`: reads the RAM tier into memory of its own for this call, or maps it, whatever `TRASH_PANDA_RAM_IN_MEMORY` says. The default (`None`) follows the setting
- README: "Loading the next model while one runs", and a paragraph in "Running a stage" on when the `Release` of a RAM-tier block arrives. The roadmap no longer has the first version of the early reads; the version for pipelines that run the same stages for many inputs in a row stays in "Out of scope for now"

### Changed
- In a final pass, the stored tensors of a RAM-tier block are dropped on a thread of its own (`trash-panda-drop`), one block at a time in the order the blocks ran, and the block's `Release` is queued when they are gone. Before, they were dropped on the compute thread. Where the model has no copy stream (the CPU, and so every test run) and for blocks of the other tiers nothing changes: they are dropped on the calling thread and announced at once. `release()`, `handle.remove()` and the profile report wait for the thread, so the RAM is back before `release()` measures it. The `event` of a `Release` is still recorded on the compute stream right after the block's GPU copy is freed. A `Release` of a RAM-tier block can now arrive after the model's last call has returned, so a queue read right after that call may not have the last one yet
- The reason: with the RAM tier memory-mapped (the default), the last tensor of the checkpoint to be dropped takes the whole mapping with it, and that took 1.1 s on the main thread at the end of the last step

### Notes
- Measured outside the library (a script that is not part of the repository, torch 2.5.1, safetensors 0.7.0): the tensors of blocks 12 and up of the diffusion model's file (16 blocks, 6.95 GB) were taken with `safe_open`, one byte per page was read, and the blocks were released one at a time. The last release took 1142 ms and the 15 before it 0 ms each; with the pages not read it took 3 ms. A second thread that woke every millisecond paused 16 ms (its normal pause on Windows) during a 1073 ms release, so Python's global lock is not held and the release can run on another thread
- Krea2 pipeline on the test machine (mapped RAM tier, 12 GPU and 20 RAM blocks, 6.1 GB of RAM in use at the start): the last step took 6.34 s against 7.64 s with the same plan before the change (the other steps 6.35 to 6.38 s). The total was 95.0 s against 94.7 s, because `release()` waits for the thread, so the 1.1 s moved there. The last RAM block was announced 1.74 s after the one before it, and a queue read right after the loop did not have it yet
- The cause of the gap that 0.0.20 left open is the mapped tensors: with `TRASH_PANDA_RAM_IN_MEMORY=1` and the same plan (20 RAM blocks) the last block was announced 0.23 s after the one before it and the last step took 6.38 s. That run took 120.9 s in total, because the 7.29 GB are read at load at 0.23 GB/s, so it is not a way to avoid the gap
- With a mapped RAM tier, the RAM of the blocks comes back all at once when the last tensor is dropped: at the start of `release()` the machine had 1.17 GB free (the process had 7.70 GB in its working set), and 8.78 GB after the hooks were removed. The `ram` events before the last one say a block is freed while its pages are still mapped, so a coordinator should read the free RAM and not add up the events

Blocks allocated on the copy stream roughly doubled the reserved memory (5.1 to 5.4 GB for 2.6 GB of blocks). On the test pipeline the text encoder's blocks (0.10 GB) are smaller than the diffusion model's (0.43 GB), so the step into the diffusion model is the larger case. Not tried with the real blocks
- The first probe of the allocator in 0.0.20 used blocks of equal size, which is why it did not show the size limit
- `preload()` is tested on the CPU only (17 tests in `tests/offload/test_preload.py`): it has not been run on the Krea2 pipeline, where the text encoder computes for 0.2 s and there is nothing to hide the reads behind
- The normal pipeline run after all the changes of this version (mapped RAM tier, 12 GPU and 20 RAM blocks, 6.5 GB of RAM in use at the start): 97.4 s in total, with passes 3 to 7 of the diffusion model at 6.32 to 6.34 s (6.34 to 6.38 s before) and the last step without the gap. Pass 1 took 22.28 s against 20.2 s in the run before, because the RAM tier was read cold at 0.38 GB/s instead of 0.42 GB/s, and one block waited 2.9 s for its copy; that path was not changed. This is inside the 94.9 to 98.3 s range of the defaults in 0.0.19

## [0.0.20] - 2026-11-03
### Added
- `OffloadHandle.subscribe()` returns a `queue.SimpleQueue` that gets a `Release` for every block that a final pass (`handle.final_pass()`) frees, in the order they are freed. A `Release` has the block's `name`; its `tier` (`"gpu"` for a block that stays on the GPU, `"ram"` or `"disk"`); `nbytes`, what the block held in that tier (its weights on the GPU, its stored weights in CPU memory, and 0 for a disk block, which holds nothing in memory between uses); `event`, a CUDA event recorded on the compute stream after the block ran, so that GPU memory the block held may be reused for work on another stream once it has completed (None without CUDA); and `queued`, the `time.perf_counter()` value when it was put on the queue. The block is already freed when its `Release` is queued, and the hook never waits for whoever reads the queue. Nothing is queued until `subscribe()` is called, so there is no setting for it. The queue is not bounded
- The profile (`TRASH_PANDA_PROFILE=1`) gives a line after a final pass, `final pass freed N blocks over X s (gpu ..., ram ...)`, with the blocks and GB per tier and the time from the first block freed to the last. With a subscriber it adds the most `Release` objects the queue held at once and how many were still unread. The line is given without a subscriber too
- The profile lists the named blocks that never ran: `blocks that never ran: a, b (X GB). If the model never uses them, consider leaving them out with skip_prefixes`. It is given once some block has run, lists up to six names and then `and N more`, and counts blocks whose weights are loaded late with `overlap=True` as well. The sizes are those of the blocks in their own tier
- README: "Running a stage" describes `final_pass()` and `subscribe()`, "Reading the profile" the two new lines, and the roadmap has the result of the allocator test

### Changed

## [0.0.19] - 2026-11-02
### Added
- `stage(..., overlap=True)`: the resident blocks are not loaded before the first call. A worker thread loads them one at a time, in the order the blocks run (the order given by `order=` or the order file), and the model starts as soon as its first block is on the GPU. A block that starts before its weights have arrived waits for them; if the loading fails, the call that needs the missing block raises a `RuntimeError` that names it, and a warning is given. Removing the handle stops the thread after the block it is loading. The weights outside the blocks, the blocks in RAM and the blocks on disk are loaded as before. Off by default

## [0.0.15] - 2026-10-29

## [0.0.13] - 2026-10-27
### Added
